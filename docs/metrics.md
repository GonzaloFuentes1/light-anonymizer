# Anonymizer evaluation metric

This document defines how we measure whether the anonymizer works. The metric is the same in
every phase and is computed by `test_bench.evaluate` on the fictitious test set
(`test_data/generated/`, generated by `scripts/generate_test_data.py`).

The core idea comes from the notebook (the original CoP 33 notebook): **it is not enough for
the document to look redacted; we have to check in the output file that the data is no longer
there.** That is why two different things are measured:

- **Recall** (did it find it?): the fraction of personal data covered by the redaction areas
  the system proposed.
- **Leaks** (can it be recovered?): which data is still present in the output file, by any
  route: extractable text, file bytes, visible pixels, original images left inside the file,
  images covered by
  a rectangle, vector paths or metadata.

A system can have high recall and still leak (for example, if it draws a black rectangle
instead of deleting the content). The acceptance criterion requires both.

## 1. Ground truth

`test_data/generated/manifest.json` describes every file and every data item it contains
(schema in `test_bench/schema.py`).

**Element**: one data item at one specific place in the file.

| Field | Meaning |
|---|---|
| `type` | `rut`, `email`, `phone`, `url`, `name`, `address`, `face`, `signature`, `qr`, or `text` (neutral reference text, with no personal data) |
| `level` | `base` (realistic and legible), `stress` (hard: tiny, mirrored, old formats, heavy noise), `out_of_scope` (documented limit: a name not on the list, a signature, handwriting) |
| `layer` | `text` (PDF text layer), `raster` (pixels), `vector` (glyphs converted to paths), `hidden` (present but invisible: optional layer turned off, off the page, white on white, under an image) |
| `polygon` | exact outline of the data item (a rotated quadrilateral where applicable) |
| `core` | faces only: eyes, nose and mouth |
| `value` | the exact text, which is unique across the whole set (it works as a *canary*) |

The codes in the manifest and in the report are in English; the `evaluation.md` report shows
them with their Spanish label (for example, `email` as "correo" and `stress` as "estres").

**Sensitive metadata item**: a data item in metadata or non-visible structures (EXIF, GPS,
EXIF thumbnail, XMP, PNG text chunks, TIFF tags, PDF metadata, annotations, attachments,
optional layers, forms, bookmarks, JavaScript, previous revisions of a PDF).

**File with an expected error**: password-protected, corrupt, empty or with a misleading
format. The system must reject it with an understandable error code.

Coordinates: in images, pixels of the EXIF-corrected geometry (that of the output); in PDF,
points in PyMuPDF's unrotated page space.

## 2. What the evaluated system delivers

1. An output folder with the redacted files (at the same relative path).
2. A JSON report (`RedactionReport` in `test_bench/schema.py`) with, for each file: output
   path, redacted areas (page, polygon, type, detector, score, status), the error if it was
   rejected, processing time and pages processed.

The phase 1 engine will produce this report as part of its audit report.

## 3. Per-element checks

| Code | Check | Where it applies |
|---|---|---|
| **C** Coverage | Fraction of the polygon covered by the union of the active redaction areas (status other than `dismissed`) on that page. Computed by rasterizing with supersampling. Threshold: ≥ 0.95. Faces: core ≥ 0.95 and full face ≥ 0.80. | all visible layers |
| **T** Extractable text | All the text of the output is extracted with two independent engines (PyMuPDF, without clipping to the page, and pdfium) and normalized. There is a leak if the full value **or a critical fragment** appears: the RUT body without its check digit, the last 7 digits of the phone, the local part of the email with `@`, the surnames of the name, the street and number of the address. | PDF |
| **B** Bytes | The value and its critical fragments are searched for in the file bytes, in every decompressed stream and in the strings of every PDF object, in UTF-8, Latin-1, UTF-16 BE and UTF-16 LE. | all |
| **P** Pixels | The output is rendered (PDF at 144 dpi, in its visible orientation) and ≥ 95 % of the polygon's pixels must have the area's uniform fill color (90 % for polygons under 20 px²). In addition, if the area looks uniform but its grayscale correlation with the input is ≥ 0.90, the pixels are still the original ones and the check fails: this way a dark face in shadow, the ghost photo on the ID card (cédula) or text under a glare do not pass as "redacted". | visible layers |
| **I** Covered images | In PDF, for every image on the page that overlaps the polygon, the image is extracted, the polygon is mapped to its coordinates and the same uniformity is required. Catches the mistake of drawing a rectangle over an image without erasing its pixels. | raster in PDF, faces in PDF |
| **O** Original images | In PDF, no input image that contains a data item may appear intact (with the same pixels) in the output, whether or not it is drawn on any page. Catches the unredacted original image that remains as an orphan object when the PDF is saved without being fully rewritten, a problem confirmed in the notebook. | raster in PDF, faces in PDF |
| **V** Vector paths | In PDF, no paths with curves (glyphs) may remain inside the polygon. Catches a rectangle drawn over vectorized text. | vector |

An element is **redacted** if it passes every check that applies to its layer (faces follow
the rule of their `raster` layer):

| Layer | Checks |
|---|---|
| `text` | C, T, B, P |
| `hidden` | T, B |
| `vector` | C, P, V |
| `raster` in an image | C, P |
| `raster` in a PDF | C, P, I, O |

An element that is not redacted is a **leak**. The report states which check failed.

**Geometry.** The output must have the same number of pages and the same *visible* size as the
input (a page with `/Rotate 90` rebuilt as a landscape page without `/Rotate` is valid). If
not, the elements on those pages count as leaks with the reason `geometry_mismatch`, because
it cannot be verified that they do not leak. Check O needs the set's input folder (the one in
the manifest) to compare the original images.

**Sensitive metadata item**: there is a leak if the canary appears in the output (structured
EXIF/XMP/PNG/TIFF/PDF readers plus the byte search), or, for non-textual data, if the
structure is still present (GPS block, EXIF thumbnail, attachment, optional layer, previous
revision).

Residual metadata that are not canaries (for example, a `Producer` field or a color profile)
are also listed as **warnings**, without counting them as leaks.

## 4. Metrics

**Recall** by type and level:

```
recall(type, level) = elements with sufficient coverage / elements of that type and level
```

For the `hidden` layer (which has no visible area), "detected" means "removed" (T and B).

**Leaks** by type and level: number and percentage of unredacted elements, with the details of
each one (file, page, value, failed check).

**Metadata leaks**: number of sensitive metadata items present in the output.

**Expected errors**: files that had to be rejected and were rejected with the correct code.
Processable files that the system rejected are listed separately; they count as not detected
in the recall, not as leaks (there is no output file to publish).

**Breakdowns** (face and OCR recall report):
- Faces: by face size in the output (height < 24, 24–48, 48–96, 96–192, ≥ 192 px), pose
  (frontal, three-quarter, profile), angle and origin (standalone photo, PDF, scan, ID card).
- Text in images: by angle (0, 90, 180, 270, 15, 45, mirrored), letter height in pixels, font,
  degradation (noise, blur, JPEG, perspective) and file category.
- RUT: with a valid or invalid check digit (it must make no difference: the check digit
  decides nothing).

**Informational metrics** (reported, never optimized at the expense of recall):
- *Over-redaction*: fraction of neutral `text` elements (including amounts and dates, which
  are decoys) covered ≥ 50 %; redaction areas that touch no personal data.
- *Text preservation* (PDF): fraction of neutral `text` elements of the text layer that remain
  extractable. Measures whether the document is still useful and accessible.
- *Time*: seconds per file, per PDF page and per image (median, p95, maximum), and peak memory
  if the report includes it. The machine it was measured on is reported.

**"Redact all text in this image" mode**: in the files where the system enabled it, the `text`
elements become targets and their recall is reported separately.

## 5. Phase 1 acceptance criterion

1. **Zero leaks** of `rut`, `email` and `phone` at the `base` level, in every category (text
   PDF, scans, rotated images, ID card, screenshots, TIFF).
2. **Zero leaks of sensitive metadata**.
3. All files with an expected error rejected with an understandable message.
4. Face and OCR recall report with the breakdowns of section 4 (no fixed threshold in this
   phase; the numbers are discussed at review).
5. Times per image and per page on CPU.

The `stress` and `out_of_scope` levels are always reported but do not block. Their purpose is
to keep the limits visible.

## 6. Validating the evaluator itself

A metric that does not detect leaks is worse than having no metric. That is why the evaluator
is validated with three baselines (`test_bench/baselines/`):

| Baseline | What it does | Required result |
|---|---|---|
| `identity` | copies the files untouched | **every** element and metadata item must show up as a leak. If one does not, the evaluator is blind to that case and gets fixed. |
| `oracle` | redacts exactly the ground truth (rasterizes and fills) and removes metadata | 100 % recall and zero leaks. If not, the ground truth or the coordinates are wrong. |
| `notebook` | the CoP 33 notebook's logic as-is | reference: shows what it covers today and what it does not |

These three runs are automated tests (`tests/test_bench/`).

The `prototype` baseline runs the real engine with every detection group on and the URLs that
are not personal applied (`DetectionOptions.everything()`): the app lets the user turn groups
off and, by decision D12, leaves those URLs unapplied by default, but the bench always measures
the full detection so its numbers stay comparable from one run to the next.
